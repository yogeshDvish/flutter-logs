# ADR-0006 — Installation identifier as device identity

Status: Accepted · 2026-10-29

## Context

One project runs on several devices; logs must be filterable per device. The reference package uses
Android's `androidInfo.id` (a build id, identical across devices of the same build) and iOS's
`identifierForVendor` (resets on uninstall) — neither supports the required model.

## Decision

- `installation_id` = a UUID generated by the client on first run, persisted in app storage.
- Server row per `(project_id, installation_id)` with label, platform, OS, app version,
  first/last seen, optional block flag.
- No hardware identifiers, advertising IDs, or personal device data.
- Reinstall produces a new installation. Blocking blocks future ingestion, not history.
- The ingestion key is shared by all installations of a project and is not a device identity.

## Alternatives

- **Hardware identifiers (IMEI, serial, MAC)** — invasive, frequently unavailable, and a privacy
  liability.
- **Vendor identifiers** (`identifierForVendor`, `androidInfo.id`) — unstable or non-unique.
- **Server-assigned device ids at first contact** — requires a registration handshake and breaks
  offline-first logging.

## Consequences

- Pseudonymous, not anonymous: logs from one installation are correlated within one project.
- The same phone in two projects is deliberately unlinkable, because rows are project-scoped.
- Reinstalls fragment history; documented in the integration guide.
- Device revocation is a best-effort control since a client can generate a new UUID at will.
